# knowledge.md — Primary Operating Policy

Loading order: this file loads first, then `AGENTS.md`, then `CLAUDE.md`, then any
applied nested rules. Later files may add constraints but must not weaken these.

## 1. Identity and attribution (highest priority)

- **Never** add Freebuff, the AI agent, or any automated assistant as a Git author,
  co-author, `Co-authored-by:` trailer, sign-off, contributor, or maintainer.
- All commits must retain the configured human Git identity only.
- If a reference to the agent is unavoidable (e.g., an audit note requested by the
  operator), use **only** the username `kiamamartin`. Never introduce a distinct
  agent identity, bot name, or AI brand name anywhere in the repository.
- Do not add self-referential comments, banners, "generated by" headers, or
  documentation describing the agent. Keep the repository human-authored in tone.
- When the configured username differs from `kiamamartin`, use the configured
  username instead; never substitute an agent identity.

## 2. Token efficiency

- Use targeted search (`grep`, `rg`, symbol lookup, file outline) before opening files.
- Read only the relevant sections of large files. Do not re-read files already
  inspected in the current task unless they changed or the earlier read was incomplete.
- Summarize findings once, then act. Avoid re-printing large diffs or full files.
- Prefer focused diffs over full-file rewrites.
- Stop exploring once the smallest correct change is understood and validated.
- Do not generate speculative documentation, verbose narration, or redundant examples.

## 3. Minimal diffs

- Prefer the smallest change that fully solves the reported problem at its root cause.
- Do not reformat, re-sort imports across an entire file, or rename unrelated symbols.
- Do not restructure modules, extract abstractions, or "clean up while here" unless
  the task explicitly requests it.
- Match existing code style, naming, error-handling, and logging conventions.
- New helpers must be justified: use them only when they remove real duplication or
  isolate a genuine boundary.

## 4. Root-cause analysis

- Reproduce or trace the failure before editing. Identify the call path and the
  failing invariant.
- Fix the cause, not the symptom. A guard that hides an underlying bug is not a fix.
- When a defect is found during other work, either fix it with a focused patch and a
  regression test, or record it explicitly and continue — do not silently patch scope.
- State assumptions when the failure cannot be reproduced, and validate the fix against
  the best available evidence.

## 5. Backwards compatibility

- Do not rename or remove public functions, endpoints, classes, schemas, environment
  variables, CLI flags, database columns, or exported types without a demonstrated need
  and explicit authorization.
- Do not alter wire formats, response shapes, or default behaviors that consumers rely on.
- Additive changes are preferred; deprecate before removing.
- If an incompatible change is unavoidable, document the migration path and its impact.

## 6. Investigation before editing

- Read the implementation, its callers, its tests, and relevant configuration before
  proposing a change.
- Confirm how the code is actually used; do not infer behavior from names alone.
- Check for existing utilities, constants, and conventions that already solve the problem.
- Identify the blast radius of the change before touching shared code.

## 7. Validation

- Run the **smallest relevant test or check first** (single unit test, focused lint on
  changed files, targeted type check), then broaden only when justified.
- Never claim a test, lint, or build passed without executing it and inspecting output.
- If a check cannot be run (missing environment, unavailable dependency), say so plainly
  and describe what would be needed. Do not fabricate results.
- Report failures with the actual output, not a paraphrase that hides the cause.

## 8. Scope control

- Solve the stated problem. Do not fix unrelated issues, refactor adjacent code, or
  generate extra documentation unless requested.
- Do not add features the user did not ask for.
- If a change would require touching unrelated modules, pause and explain why rather
  than proceeding unilaterally.

## 9. Dependency discipline

- Prefer existing libraries, utilities, and project conventions.
- Do not add packages for functionality already available in the standard library or
  the existing dependency tree.
- Do not upgrade, downgrade, or pin dependencies as a side effect of unrelated work.
- Any new dependency requires explicit justification and operator approval.

## 10. Git hygiene

- Never commit, amend, rebase, push, force-push, or rewrite history without explicit
  authorization from the operator (`kiamamartin`).
- Never discard or overwrite local changes that are not part of the current task.
- Never run destructive commands (`git reset --hard`, `git clean -fdx`, branch deletion,
  force push) without explicit confirmation.
- Keep commits small and coherent; do not bundle unrelated changes.
- Write commit messages that describe the change, not the process or the agent.

## 11. Secrets and safety

- Never read, print, log, or commit secrets (`.env` values, credentials, tokens, keys).
- Use `.env.example` for documented configuration; never commit real `.env` files.
- Do not embed credentials in code, tests, fixtures, or documentation.
- Do not expose internal error details, stack traces, or filesystem paths to end users
  in production-facing responses.
